Alur Kerja Vibe Coding

Dari Kebutuhan ke Issue: Tahapan Menentukan Apa yang Ingin Dibuat Sebelum Menyuruh AI

Ketika meminta AI "buatkan aplikasi seperti ini", pada awalnya hasil kerja yang berjalan muncul dengan sangat cepat dan mengagumkan. Namun, setiap kali Anda menambah fitur baru, fitur sebelumnya justru rusak, dan Anda sendiri bingung mana yang sudah selesai dan mana yang belum. Panduan tahapan ini dirancang untuk mencegah kekacauan tersebut: merumuskan apa yang ingin dibuat dalam bentuk tulisan terlebih dahulu, membaginya menjadi tugas-tugas kecil yang dikelola lewat GitHub Issues, lalu menyerahkannya satu per satu kepada AI.

Pembaca
Orang yang tidak menulis kode manual tetapi membuat aplikasi menggunakan bantuan AI. Jika belum memiliki akun GitHub, kita akan membuatnya di Tahap 0.
Alat Bantu
AI yang dapat mengoperasikan file dan terminal (seperti Claude Code, Cursor, Antigravity, dll.) dan GitHub. Dalam alur kerja ini, seluruh perintah di terminal diserahkan kepada AI. Jika hanya menyusun dokumen pada Tahap 1–4, AI percakapan biasa seperti ChatGPT pun sudah cukup.
Studi Kasus
Seluruh contoh dalam artikel ini menggunakan studi kasus fiktif: "Aplikasi Manajemen Kehadiran Temu Komunitas (Offkai / Gathering)".

Alur Keseluruhan

Alur kerja ini terdiri dari 6 tahapan utama. Setiap tahap merupakan serah-terima sederhana: "menerima hasil dari tahap sebelumnya, lalu menghasilkan output untuk tahap berikutnya". Inti perencanaan ada pada 5 tahap pertama, sedangkan tahap ke-6 (Eksekusi) adalah mengeksekusi Issue yang telah dibuat satu per satu. Sebelum mulai, ada tahap persiapan awal (Tahap 0) untuk menyiapkan akun GitHub dan peralatan, yang cukup dilakukan sekali saja.

Mengapa Urutan Ini?

Ada 3 alasan utama:

  • Apa yang ingin dibuat belum benar-benar jelas sampai kita menuangkannya ke dalam kata-kata. Hasil AI yang melenceng sering kali bukan kesalahan AI, melainkan karena kebutuhan dari pihak pemesan memang belum matang. Definisi kebutuhan dan spesifikasi ditulis bukan hanya untuk AI, melainkan untuk memperjelas pikiran Anda sendiri.
  • Jika spesifikasi sudah siap di awal, hasil keluaran AI akan jauh lebih konsisten dan stabil. Alih-alih mengulang asumsi dan instruksi dasar di setiap sesi percakapan, Anda cukup menyematkan dokumen spesifikasi agar AI selalu memulai dari konteks yang sama.
  • Memecahnya menjadi bagian kecil memungkinkan verifikasi langsung. "Aplikasi secara keseluruhan" mustahil diverifikasi sekaligus secara menyeluruh, tetapi "bisa memilih Ya/Tidak pada opsi tanggal" bisa diuji dalam 5 menit. Issue adalah tempat mencatat unit verifikasi tersebut.

Berikutnya, kita mulai dari persiapan awal (Tahap 0) yang cukup dilakukan sekali, lalu mengupas tuntas ke-6 tahap dengan struktur pola yang sama: Tujuan, Masukan & Keluaran, Prompt untuk AI, Templat Hasil Kerja, Contoh Kasus Nyata (Aplikasi Temu Komunitas), Kriteria Selesai (Checklist), serta Jebakan/Kesalahan Umum. Prompt dan templat dapat langsung disalin dan digunakan.

Persiapan Awal

Buat akun GitHub sendiri, lalu serahkan instalasi alat dan pembuatan repositori kepada AI

Hanya Sekali di Awal

Tujuan

Tahap 1–6 memanfaatkan GitHub sebagai "tempat penyimpanan catatan dan progres". Ketika membuat Issue di Tahap 5 dan membuat Pull Request di Tahap 6, proses akan terhenti jika sisi GitHub belum siap. Oleh karena itu, kita selesaikan persiapannya di sini.

Ada 3 persiapan: pembuatan akun GitHub, pemasangan alat gh (GitHub CLI) untuk mengelola GitHub lewat terminal, dan pembuatan repositori aplikasi. Dari ketiga hal ini, yang perlu Anda lakukan sendiri hanyalah membuat akun. Dua langkah sisanya serahkan kepada AI. Anda tidak perlu membuka terminal sendiri.

Masukan dan Keluaran

Masukan
Alamat email, serta folder tempat aplikasi disimpan (folder tempat Anda membuka AI).
Keluaran
Akun GitHub yang sudah login, kondisi AI yang siap mengoperasikan GitHub, dan repositori aplikasi baru yang siap digunakan.

1. Buat Akun GitHub (Lakukan Sendiri)

  1. Buka github.com/signup, lalu masukkan alamat email dan kata sandi Anda.
  2. Tentukan username. Hanya gunakan huruf latin, angka, dan tanda hubung (-). Karena username akan menjadi bagian dari URL repositori, sebaiknya tentukan nama yang rapi sejak awal.
  3. Masukkan kode verifikasi yang dikirimkan ke email Anda. Pilih paket gratis (Free), ini sudah lebih dari cukup.
  4. Aktifkan otentikasi dua faktor (Two-Factor Authentication / 2FA) di pengaturan keamanan akun menggunakan aplikasi autentikator di ponsel.

Kata sandi dan kode verifikasi email harus Anda masukkan sendiri secara langsung di browser, jangan pernah diberikan kepada AI.

2. Alat dan Repositori (Serahkan ke AI)

Buka AI di folder tempat Anda ingin membuat aplikasi, lalu berikan instruksi di bawah ini apa adanya. AI akan memasang alat bantu yang diperlukan, memandu proses login ke GitHub, membuat repositori, dan menghubungkannya.

Berikan ke AI
Tolong siapkan lingkungan kerja GitHub untuk saya. Saya tidak menulis kode dan tidak ingin mengoperasikan terminal secara manual.

Yang perlu kamu lakukan:
1. Periksa apakah perintah resmi GitHub 'gh' sudah terpasang, jika belum tolong pasang (sekaligus pasang 'git' jika belum ada).
2. Periksa status login dengan 'gh auth status'. Jika belum login, jalankan 'gh auth login'. Ketika tiba saatnya saya harus menekan tombol di browser, beri tahu saya secara ringkas: "apa yang harus ditekan dan di mana".
3. Konfigurasikan folder ini agar dikelola oleh Git, buat README.md dan folder docs/ (berisi README.md sebagai panduan), lalu lakukan commit pertama.
4. Buat repositori private (hanya bisa dilihat oleh saya) di GitHub bernama {nama-aplikasi. huruf kecil dan tanda hubung, contoh: offkai-app} menggunakan 'gh repo create', lalu hubungkan folder ini dan push.
5. Terakhir, buka repositori tersebut di browser dengan 'gh repo view --web', dan minta saya memastikan apakah README sudah terlihat.

Aturan yang harus dipatuhi:
- Laporkan setiap langkah yang telah kamu lakukan dalam 1 baris dengan bahasa yang mudah dipahami orang awam.
- Jika di tengah jalan membutuhkan tindakan saya, berhenti dan tunggu arahan saya.
- Jangan pernah meminta kata sandi atau kode verifikasi saya.

Di tengah proses, AI akan sekali meminta Anda untuk "membuka browser". Ini adalah proses otorisasi login. Halaman GitHub akan terbuka di browser, Anda cukup menempelkan kode 8 digit yang diberikan oleh AI lalu menekan tombol "Authorize". Hanya ini tindakan yang perlu Anda lakukan, selebihnya AI yang akan menyelesaikan semuanya.

Terakhir, jika repositori yang terbuka di browser sudah menampilkan file README dan folder docs, maka persiapan selesai. Folder docs akan menjadi tempat menyimpan Dokumen Kebutuhan, Spesifikasi, dan Desain Sistem yang dibuat pada Tahap 1–3.

Referensi: Perintah yang dijalankan AI di balik layar (Anda tidak perlu mengetiknya)
Pemasangan Alat
# Mac
brew install gh
# Windows (PowerShell)
winget install GitHub.cli
winget install Git.Git

# Login ke GitHub dan periksa status
gh auth login
gh auth status
Pembuatan Repositori
git init
echo "# {nama-aplikasi}" > README.md
mkdir docs
echo "Dokumen kebutuhan, spesifikasi, dan desain disimpan di sini" > docs/README.md
git add .
git commit -m "Commit perdana"
gh repo create {nama-aplikasi} --private --source=. --push
gh repo view --web

Gunakan referensi ini untuk mencocokkan apa yang sedang dilakukan jika nama-nama perintah ini muncul dalam laporan AI.

Kriteria Selesai (Checklist)

  • Berhasil login ke GitHub di browser dan otentikasi dua faktor (2FA) sudah aktif
  • Ketika meminta AI menjalankan gh auth status, muncul laporan status yang menyertakan teks "Logged in"
  • Saat membuka repositori di browser, file README dan folder docs sudah terlihat
  • Terdapat label "Private" di samping nama repositori

Jebakan & Kesalahan Umum

Mencoba mengetik perintah sendiri lalu buntu. Dalam alur kerja ini, seluruh proses yang melibatkan terminal dipercayakan ke AI. Jika muncul istilah asing dalam laporan AI, cukup tanyakan: "Apa maksudnya langkah tadi?".
Melewatkan otorisasi login. Jika instruksi AI untuk "klik tombol di browser" diabaikan, pendaftaran Issue di Tahap 5 akan gagal karena error "belum terotentikasi". Anda cukup meminta AI: "Pandu saya untuk login sekali lagi" untuk mengulanginya.
Niatnya private tetapi terbuat sebagai public. Sebelum memasukkan data riil seperti lokasi atau biaya, pastikan label di samping nama repositori adalah Private. Anda bisa meminta AI: "Ubah repositori ini menjadi private" jika keliru.

Definisi Kebutuhan (Requirements)

Merangkum siapa penggunanya, apa masalahnya, dan apa manfaat yang diharapkan ke dalam 1 lembar dokumen

Tahap Inti

Tujuan

Ini bukan tahap membuat daftar fitur panjang. Ini adalah tahap mendefinisikan "masalah nyata yang dihadapi" dan "manfaat/solusi yang melegakan". Jika bagian ini kabur, seluruh tahapan berikutnya akan berjalan dalam ketidakpastian.

Kuncinya adalah: jangan menyuruh AI langsung menulis dokumennya, melainkan biarkan AI mewawancarai Anda. Sembari Anda menjawab pertanyaannya, kebutuhan aplikasi akan mengkristal dengan sendirinya.

Masukan dan Keluaran

Masukan
Ide dasar di kepala Anda. Belum rapi pun tidak masalah.
Keluaran
Dokumen Definisi Kebutuhan. Cukup ringkas sepanjang 1 lembar A4.

Prompt untuk AI

Berikan ke AI
Kamu adalah pewawancara profesional yang bertugas menggali kebutuhan aplikasi yang akan dibuat.
Saya adalah orang awam yang tidak menulis kode. Jangan gunakan istilah teknis, dan ajukan pertanyaan kepada saya satu per satu secara bertahap.

Aplikasi yang ingin saya buat: {Jelaskan dalam satu kalimat. Contoh: Aplikasi untuk mengelola kehadiran temu komunitas / gathering offline}

Lanjutkan wawancara dengan pertanyaan sampai hal-hal berikut jelas:
- Siapa saja yang akan menggunakannya (bedakan peran, misal: panitia/penyelenggara dan peserta)
- Bagaimana cara yang dilakukan saat ini, dan kendala apa yang dialami
- Jika aplikasi ini ada, apa nilai/kemudahan terbesar yang dirasakan
- Batasan fitur minimal yang sudah dianggap "cukup berfungsi" (MVP)
- Hal-hal yang secara tegas TIDAK PERLU dibuat sekarang

Setelah merasa informasinya cukup, buatlah Dokumen Definisi Kebutuhan sesuai templat di bawah ini.
Bagian yang belum pernah saya jawab wajib ditulis "Belum Ditentukan", jangan mengarang atau berasumsi sendiri.

Templat:
# Dokumen Definisi Kebutuhan
## Tujuan (1 kalimat)
## Pengguna Sasaran
## Kendala Saat Ini
## Fitur Wajib (Harus Ada)
## Fitur Tambahan (Bagus Jika Ada)
## Yang Tidak Dibuat (Out of Scope)
## Kriteria Penyelesaian

Contoh Penerapan

Dokumen Definisi Kebutuhan (Aplikasi Temu Komunitas / Gathering)

Tujuan (1 kalimat)

Memudahkan panitia menentukan jadwal dan mendata kehadiran gathering komunitas tanpa harus menyisir riwayat chat grup secara manual.

Pengguna Sasaran

  • Penyelenggara / Panitia (1 orang, mengadakan temu komunitas sebulan sekali berkapasitas 10–20 orang)
  • Peserta (campuran anggota lama dan peserta baru, mengakses via ponsel/smartphone)

Kendala Saat Ini

  • Menanyakan opsi tanggal lewat chat grup membuat balasan tertimbun sehingga sulit menghitung siapa saja yang bisa hadir
  • Lokasi dan besaran iuran selalu ditanyakan berulang kali
  • H-1 acara selalu ada yang bertanya: "Acaranya jadi besok kan?"

Fitur Wajib (Harus Ada)

  • Penyelenggara dapat membuat agenda temu dan menyediakan beberapa opsi tanggal/waktu
  • Peserta dapat merespons tiap opsi tanggal dengan pilihan: Bisa (○), Ragu-ragu (△), atau Tidak Bisa (×)
  • Penyelenggara dapat melihat daftar nama dan rekapitulasi jumlah orang yang memilih "Bisa" pada setiap opsi tanggal
  • Informasi lokasi dan besaran iuran tertulis jelas di halaman acara

Fitur Tambahan (Bagus Jika Ada)

  • Email pengingat otomatis terkirim H-1 sebelum acara dimulai

Yang Tidak Dibuat (Out of Scope)

  • Pembayaran iuran secara online (dilakukan tunai di lokasi)
  • Berbagi foto acara (cukup gunakan chat grup yang sudah ada)
  • Fitur chat antar peserta di dalam aplikasi

Kriteria Penyelesaian

Penentuan tanggal dan pendataan kehadiran untuk acara gathering berikutnya dapat diselesaikan tuntas hanya melalui aplikasi ini tanpa bantuan polling di chat grup.

Kriteria Selesai (Checklist)

  • "Tujuan" tertulis padat dalam 1 kalimat jelas
  • Pengguna dipisahkan menurut perannya (misal: panitia vs peserta)
  • Terdapat minimal 3 poin pada bagian "Yang Tidak Dibuat"
  • "Kriteria Penyelesaian" dapat diuji dan dibuktikan secara nyata
  • Sama sekali tidak mengandung istilah teknis (database, framework, dsb.)

Jebakan & Kesalahan Umum

Memulai dari daftar fitur acak. Mendaftar "login, posting, like, notifikasi" tanpa memahami siapa yang sedang menghadapi masalah apa akan membuat Anda bingung menentukan prioritas mana yang wajib dan mana yang sekunder.
Kolom "Yang Tidak Dibuat" dibiarkan kosong. Jika tidak ada batasan tegas, AI akan terus berinisiatif menambahkan fitur karena niat baik. Menentukan apa yang tidak perlu dibuat adalah separuh dari kesuksesan definisi kebutuhan.
Menyuruh AI mengarang seluruh dokumen. Dokumen kebutuhan yang dibuat tanpa wawancara hanyalah imajinasi AI tentang aplikasi rata-rata. Kendala nyata di lapangan hanya Anda yang mengetahuinya.

Dokumen Spesifikasi

Menerjemahkan kebutuhan menjadi "Layar Halaman, Data, dan Aturan Main"

Tahap Inti

Tujuan

Dokumen kebutuhan menjelaskan "untuk apa aplikasi dibuat". Dokumen spesifikasi menerjemahkannya ke dalam "apa saja wujud konkretnya": ada berapa layar tampilan, apa yang bisa dilakukan di tiap layar, data apa yang harus disimpan sistem, serta siapa yang berhak melakukan apa.

Ini adalah tahap tepat satu langkah sebelum ranah teknis. Bukan menulis "tabel apa yang dibuat di database", melainkan tetap dalam bahasa manusia sehari-hari seperti: "Sebuah acara gathering memiliki nama acara, opsi tanggal, dan lokasi".

Masukan dan Keluaran

Masukan
Dokumen Definisi Kebutuhan dari Tahap 1.
Keluaran
Dokumen Spesifikasi yang mencakup 6 bagian: Daftar Layar, Data yang Dikelola, Aturan Main, Yang Tidak Dibuat, Glosarium Istilah, dan Usulan Tambahan.

Prompt untuk AI

Berikan ke AI
Berdasarkan Dokumen Definisi Kebutuhan berikut, tolong susun Dokumen Spesifikasi. Saya adalah orang awam yang tidak menulis kode.

Aturan yang wajib dipatuhi:
- Jangan menulis pilihan teknologi (bahasa pemrograman, database, library).
- Jangan menambah fitur baru di luar Dokumen Definisi Kebutuhan. Jika ada ide bagus, pisahkan di bagian paling akhir sebagai "Usulan Tambahan".
- Jika ada hal yang meragukan atau belum jelas, tanyakan kepada saya terlebih dahulu sebelum mulai menulis.
- Bagian "Yang Tidak Dibuat" wajib diwarisi dari Dokumen Definisi Kebutuhan.

Format Dokumen Spesifikasi:
# Dokumen Spesifikasi
## Daftar Layar (Nama layar, siapa yang mengakses, dan apa yang bisa dilakukan)
## Data yang Dikelola (Informasi yang perlu diingat sistem, ditulis dalam bahasa awam)
## Aturan Main / Kebijakan (Siapa boleh apa, dan apa yang TIDAK boleh dilakukan)
## Yang Tidak Dibuat (Out of Scope)
## Glosarium Istilah (Definisi istilah yang digunakan dalam dokumen ini)
## Usulan Tambahan (Fitur opsional yang diusulkan AI; keputusan adopsi ada di tangan saya)

Daftar Layar

LayarSiapaHal yang Dapat Dilakukan

Daftar AcaraSemua PenggunaMelihat daftar acara yang berkaitan, diurutkan dari yang terbaru. Penyelenggara dapat menekan tombol "Buat Acara Baru"
Buat AcaraPenyelenggaraMengisi judul acara, deskripsi, lokasi, iuran, serta memasukkan beberapa opsi jadwal (tanggal & jam)
Detail AcaraSemua PenggunaMelihat lokasi dan iuran. Peserta memilih Ya (○) / Ragu (△) / Tidak (×) pada tiap opsi jadwal. Penyelenggara melihat rekapitulasi nama dan jumlah peserta

Data yang Dikelola

  • Pengguna: Nama tampilan, alamat email
  • Acara: Nama acara, deskripsi, lokasi, besaran iuran, identitas panitia penyelenggara, opsi jadwal (kumpulan tanggal dan jam)
  • Respons Kehadiran: Pengguna mana, untuk opsi jadwal mana, memilih Ya (○), Ragu (△), atau Tidak (×). Setiap orang memiliki 1 jawaban per opsi jadwal, dan dapat mengubahnya sewaktu-waktu

Aturan Main / Kebijakan

  • Hanya pengguna yang sudah login yang dapat membuat acara. Pembuat acara otomatis menjadi Penyelenggara
  • Hanya Penyelenggara yang berhak mengedit atau menghapus acara terkait
  • Pengguna yang login dapat mengisi kehadiran. Jawaban milik orang lain tidak dapat diubah

Yang Tidak Dibuat (Out of Scope)

  • Pengumpulan iuran secara daring, berbagi foto acara, fitur chat antar-peserta (diwarisi dari Dokumen Kebutuhan)
  • Pemisahan status acara publik vs privat (pada versi awal, diasumsikan hanya orang yang memiliki tautan/link yang dapat melihat)

Usulan Tambahan

  • Penyelenggara dapat menekan tombol "Tetapkan Tanggal Ini", sehingga tanggal terpilih akan disematkan di bagian paling atas halaman detail acara. (Keputusan adopsi diserahkan kepada pengguna)

Kriteria Selesai (Checklist)

  • Kolom "Siapa" tertera jelas di setiap baris tabel daftar layar
  • Seluruh fitur "Wajib" di Tahap 1 terakomodasi di salah satu layar
  • Larangan tertulis eksplisit di bagian "Aturan Main" (misal: tidak dapat mengubah jawaban orang lain)
  • Bagian "Yang Tidak Dibuat" selaras dan konsisten dengan Tahap 1
  • Inisiatif fitur baru dari AI terisolasi rapi di bagian "Usulan Tambahan" dan tidak tercampur ke badan utama

Jebakan & Kesalahan Umum

Dokumen spesifikasi terlalu panjang dan membengkak. Jika jumlah layar melebihi 10 layar, berarti fitur wajib di Dokumen Kebutuhan terlalu banyak. Kembalilah ke Tahap 1 dan turunkan sebagian fitur menjadi "Fitur Tambahan".
Tercampur bahasan implementasi teknis. Kalimat seperti "Autentikasi menggunakan Supabase" atau "Dibuat dengan React" adalah sarana/alat, bukan spesifikasi. Sarana teknis ditetapkan di Tahap 3 (Desain Sistem). Mencampurnya di sini akan membuat diskusi spesifikasi dan teknologi saling tumpang tindih.
Mengadopsi seluruh usulan tambahan dari AI. Usulan AI sering kali hanya sekadar mendaftar fitur generik yang umum di pasaran. Hanya adopsi usulan yang benar-benar menjawab kendala di Dokumen Kebutuhan.

Dokumen Desain Sistem (Architecture)

Menerjemahkan "apa saja komponennya" menjadi "bagaimana cara membuatnya", serta mendokumentasikan pilihan teknologi di satu tempat

Tahap Inti

Tujuan

Pada tahap spesifikasi kita tidak menyebut teknologi sama sekali. Dokumen desain sistem adalah tahap menentukan dengan alat apa dan arsitektur seperti apa spesifikasi tersebut diwujudkan. Di sinilah "pilihan teknologi", "struktur tabel data", dan "mekanisme hak akses" ditetapkan.

Anda tidak harus paham cara memilih teknologi sendiri. Biarkan AI yang merekomendasikannya, tetapi wajibkan AI menuliskan alasannya dalam bahasa yang Anda pahami, dan catat keputusan itu di satu tempat. Tanpa dokumen desain, AI akan berganti-ganti teknologi atau struktur data di setiap sesi percakapan baru, dan kode antar-Issue akan saling bertabrakan.

Masukan dan Keluaran

Masukan
Dokumen Spesifikasi dari Tahap 2.
Keluaran
Dokumen Desain Sistem (Teknologi & Alasan, Alur Navigasi, Struktur Data, Mekanisme Hak Akses, Layanan Eksternal, Metode Verifikasi Pengujian, Konsultasi Perubahan Spesifikasi).

Prompt untuk AI

Berikan ke AI
Berdasarkan Dokumen Spesifikasi berikut, tolong buatkan Dokumen Desain Sistem. Saya orang awam yang tidak menulis kode, namun saya harus bisa menjelaskan "mengapa teknologi ini yang dipilih" kepada orang lain setelah membaca dokumen ini.

Aturan yang wajib dipatuhi:
- Saat memilih teknologi, bandingkan maksimal 2 kandidat utama, lalu berikan rekomendasi beserta alasannya. Alasan harus dalam bahasa awam yang mudah saya mengerti (contoh: "Login, database, dan hosting sudah terintegrasi dalam satu layanan gratis").
- Utamakan arsitektur yang gratis (free tier) atau berbiaya sangat minim untuk memulai.
- Jangan menambah fitur baru. Jika demi kemudahan teknis ada spesifikasi yang perlu diubah, jangan diubah langsung, melainkan tulis di bagian akhir sebagai "Konsultasi Perubahan Spesifikasi".
- Setiap kali menggunakan istilah teknis, sertakan penjelasan singkat saat pertama kali muncul.
- Jika ada hal yang meragukan, tanyakan kepada saya terlebih dahulu sebelum mulai menulis.

Format Dokumen Desain Sistem:
# Dokumen Desain Sistem

Mengubah spesifikasi diam-diam demi kemudahan teknis. Mengurangi fitur karena alasan "kodingnya rumit" tidak boleh dilakukan sepihak di dokumen desain. Kembalilah ke spesifikasi untuk mengubahnya secara resmi agar dekomposisi tugas tidak bingung menentukan acuan.

Dekomposisi Tugas (Task Breakdown)

Memecah pekerjaan menjadi unit tugas yang bisa diselesaikan dalam 1 sesi AI dan dapat langsung diverifikasi jalannya

Tahap Inti

Tujuan

Jika Anda langsung menyerahkan dokumen spesifikasi dan desain ke AI sambil berkata "buatkan semuanya sekarang", maka saat ada yang rusak di tengah jalan, Anda tidak punya titik kembali yang jelas. Kita perlu memecah fitur spesifikasi mengikuti urutan desain menjadi tugas-tugas kecil yang bisa diselesaikan dan diuji satu per satu, lalu menentukan urutan pengerjaannya.

Standar ukurannya hanya satu: Ketika tugas itu selesai dikerjakan, bisakah Anda mengujinya sendiri di aplikasi dan memastikan dengan yakin bahwa tugas itu "sudah berfungsi"? Jika belum bisa, berarti tugas itu terlalu besar, atau ada tugas prasyarat yang harus dikerjakan terlebih dahulu.

Masukan dan Keluaran

Masukan
Dokumen Spesifikasi dari Tahap 2 dan Dokumen Desain Sistem dari Tahap 3.
Keluaran
Daftar Tugas Berurutan, lengkap dengan nama tugas, kriteria selesai yang dapat diuji, nomor urut, dan ketergantungan (dependensi).

Prompt untuk AI

Berikan ke AI
Berdasarkan Dokumen Spesifikasi dan Dokumen Desain Sistem berikut, tolong pecah pekerjaan ini menjadi tugas-tugas pengembangan (task breakdown).

Kriteria pembagian tugas:
- Setelah 1 tugas selesai dikerjakan, saya harus bisa mencoba aplikasinya langsung dan memverifikasi bahwa fitur itu "berfungsi".
- Ukuran 1 tugas harus realistis diselesaikan dalam 1 sesi kerja bersama AI (dalam hitungan beberapa jam).
- Tugas pertama harus berupa alur paling ramping (end-to-end tipis), misalnya: "Bisa login dan muncul halaman daftar acara yang masih kosong".
- Tuliskan "Kriteria Selesai" untuk setiap tugas dalam bentuk kalimat yang bisa saya uji langsung di layar ("Muncul tampilan ...", "Ketika tombol X ditekan maka ...").
- Beri nomor urut dan cantumkan ketergantungan (dependensi) jika membutuhkan tugas sebelumnya.
- Hal-hal pada "Yang Tidak Dibuat" jangan dijadikan tugas.
- Pegang teguh pilihan teknologi di Dokumen Desain Sistem, jangan mengubah stack teknologi.

  - [ ] ...

Di bagian akhir, tuliskan ringkasan total jumlah tugas dan alasan pemilihan urutan pengerjaan tersebut secara singkat.

Aturan Pembagian Tugas

1 Tugas = 1 Perubahan Utuh yang Berfungsi

Satu tugas nantinya akan menjadi 1 Pull Request (satu bundel perubahan kode). Ukuran sebesar "Seluruh Fitur Login & Autentikasi" terlalu luas; jika macet di tengah jalan semuanya akan berantakan. Pecahlah menjadi unit yang jelas seperti "Bisa login dan menampilkan profil" dan "Bisa logout".

Tugas Induk Hanya Berfungsi Mengelompokkan

Buat 1 Tugas Induk seperti "Aplikasi Temu Komunitas v1" yang mendaftar seluruh sub-tugas untuk memantau progres keseluruhan. Tugas induk tidak memuat instruksi pengerjaan kode langsung. Pada Tahap 5, kita akan membahas cara penulisan agar tugas induk tidak tertutup otomatis secara prematur.

Pecah Seluruh Tugas di Awal Sebelum Mulai Menulis Kode

Jika Anda baru memecah tugas di tengah-tengah pengerjaan kode ("eh, bagian ini kita pisah saja deh"), Anda akan kehilangan kendali tentang bagian mana yang sudah beres dan mana yang belum. Seluruh pemilahan tugas wajib diselesaikan tuntas di tahap ini.

  • Hubungan dependensi bersifat searah sehingga pengerjaan berurutan tidak akan menemui jalan buntu
  • Seluruh fitur "Wajib" pada dokumen kebutuhan terakomodasi dalam salah satu tugas

Kriteria selesai berbunyi "Mengimplementasikan fitur X". Kalimat "Mengimplementasikan fitur kehadiran" tidak dapat diverifikasi secara visual. Gantilah menjadi: "Ketika menekan tombol Ya, pilihan tersimpan dan tetap ada saat halaman dimuat ulang (refresh)".

Tahap Inti

Tujuan

Daftar tugas yang telah disusun pada Tahap 4 kini didaftarkan satu per satu sebagai GitHub Issue. Alasan menggunakan Issue dan bukan sekadar catatan obrolan atau aplikasi notes adalah:

Perintah gh CLI

Membuat 5 buah Issue secara manual lewat website GitHub memakan waktu yang cukup menyita perhatian. Dengan adanya alat gh (GitHub CLI) yang disiapkan di Tahap 0, AI dapat mendaftarkan, menampilkan, memeriksa isi, dan memperbarui seluruh Issue secara otomatis. Dua baris terakhir pada prompt di atas adalah instruksi untuk memanfaatkan kemampuan ini.

Pengecekan dan perbaikan setelah pendaftaran pun cukup diserahkan kepada AI.

Berikan ke AI (Pemeriksaan & Perbaikan)
Saya ingin memeriksa Issue yang baru didaftarkan:
- Tampilkan daftarnya dengan 'gh issue list'
- Tampilkan isi lengkap Issue #{nomor}
- Perbarui daftar checklist pada Issue Induk #{nomor-induk} dengan nomor-nomor sub-issue yang sudah pasti terbentuk

Jika terjadi kendala saat menjalankan perintah, biasanya sesi login dari Tahap 0 kedaluwarsa. Cukup minta AI: "Periksa status dengan gh auth status, dan pandu saya jika perlu login ulang".

Referensi: Perintah yang dijalankan AI di balik layar (Anda tidak perlu mengetiknya)
Perintah gh yang Sering Digunakan
# Membuat Issue Induk (isi dibaca dari file markdown. Perintah mengembalikan nomor issue baru)
gh issue create --title "chore: Aplikasi Temu Komunitas v1 (Induk)" --body-file parent.md

# Membuat Sub-Issue (sekaligus menyematkan label)
gh issue create --title "feat: Respons kehadiran pada opsi tanggal" --body-file issue-4.md --label enhancement

# Melihat daftar issue / melihat isi 1 issue
gh issue list
gh issue view 4

# Memperbarui isi Issue Induk setelah nomor sub-issue diketahui
gh issue edit 1 --body-file parent.md

# Menutup issue yang selesai (tidak perlu jika sudah otomatis via Closes #4 pada PR)
gh issue close 4

Mengirim teks isi issue menggunakan parameter --body-file lebih aman dan file salinannya tersimpan di lokal komputer sehingga dapat ditinjau kembali sewaktu-waktu.

Eksekusi

Serahkan Issue satu per satu kepada AI, verifikasi kriteria selesai sendiri, lalu merge dan tutup

Ulangi Per Satu Tugas

Tujuan

Sampai di sini, unit kerja untuk AI dan standar pengujian tuntasnya sudah lengkap tersedia. Tahap eksekusi adalah mengeksekusi unit-unit tersebut dari atas ke bawah. Jika Tahap 1–5 dipersiapkan dengan cermat, tahap eksekusi ini akan berlangsung sangat mulus dan terukur.

Langkah Kerja

  1. Pilih nomor Issue berikutnya yang dependensinya sudah terpenuhi.
  2. Minta AI: "Tolong baca dan kerjakan Issue #nomor". Lampirkan dokumen spesifikasi dan desain di awal sesi percakapan agar asumsi AI tidak bias. Jika alat gh terpasang, AI bisa langsung membaca isi Issue sendiri.
  3. Saat AI menyatakan "sudah selesai", minta AI tersebut: "Tuliskan ringkasan seluruh perubahan kode ke dalam file review.md untuk ditinjau". Lalu tempelkan file tersebut ke sesi percakapan AI yang baru dan terpisah untuk direview secara objektif. AI pada sesi yang sama cenderung menilai kodingannya sendiri terlalu lunak.
  4. Salin masukan/catatan dari sesi review, lalu tempelkan kembali ke sesi AI pengembang untuk diperbaiki.
  5. Minta AI pengembang: "Jalankan aplikasinya", lalu buka alamat URL lokal di browser. Uji setiap poin Kriteria Selesai pada Issue dengan tangan Anda sendiri. Jika ada yang belum sesuai, kembali ke langkah 2.
  6. Minta AI: "Buat Pull Request dan cantumkan Closes #nomor di keterangannya". Buka Pull Request tersebut di antarmuka web GitHub, lalu tekan tombol "Merge pull request". Issue akan tertutup secara otomatis.
  7. Minta AI: "Beri tanda centang pada sub-issue #nomor di Issue Induk", lalu lanjutkan ke Issue berikutnya.

Menginstruksikan Pengerjaan
Tolong implementasikan Issue berikut. Jangan menambah fitur di luar dokumen spesifikasi, dan patuhi pilihan teknologi serta struktur data yang telah ditetapkan di dokumen desain sistem.
Setelah kamu yakin semua kriteria selesai terpenuhi, jelaskan apa saja yang telah kamu verifikasi dan bagaimana caranya sebelum melaporkan bahwa pekerjaan "selesai".

Jebakan & Kesalahan Umum

Percaya begitu saja pada laporan AI "sudah selesai" lalu langsung merge. Kriteria selesai dibuat agar Anda bisa mencobanya langsung. Tombol merge ditekan oleh Anda, maka langkah verifikasi mandiri wajib dijalankan. Melewatkannya akan membuat persiapan Tahap 1–5 sia-sia.
Melakukan review di sesi percakapan yang sama. Jika Anda bertanya "apakah ada masalah pada kode ini?" kepada AI yang baru saja menulis kodenya, hampir pasti jawabannya adalah "tidak ada masalah". Cukup memindahkan kode ke sesi chat baru, kualitas review akan meningkat drastis.
Mengubah spesifikasi di tengah eksekusi. Jika saat mencoba aplikasi timbul ide "eh, lebih bagus kalau ditambah fitur ini", jangan langsung dikerjakan di sesi tersebut. Buatlah Issue baru dan tambahkan ke Issue Induk. Selesaikan Issue yang sedang berjalan sesuai kriteria aslinya terlebih dahulu.

Penerapan Menggunakan Claude Code

Penulis menjalankan alur kerja ini menggunakan Claude Code. Alur 6 tahap di atas tetap dapat berjalan tanpa Claude Code, tetapi Claude Code memiliki kemampuan menyimpan prosedur rutin sebagai "slash command" sehingga bagian berulang di Tahap 4–6 dapat diotomatisasi secara signifikan.

Catatan penting terlebih dahulu: Perintah /issue-create dan /issue-complete yang dibahas di bawah ini adalah perintah kustom buatan penulis sendiri, bukan fitur bawaan pabrik Claude Code. Di Claude Code standar, Anda cukup menempelkan prompt dari masing-masing tahap di atas untuk mendapatkan hasil yang persis sama. Perintah kustom baru perlu dibuat jika Anda sudah mulai merasa bosan menempelkan prompt yang sama berulang kali.

Rincian Alur di dalam /issue-complete (4 Sub-Tahap)

  1. Perancangan (Desain Sesi). Membaca Issue, dokumen desain Tahap 3, serta konvensi proyek, lalu menulis rencana implementasi spesifik untuk Issue tersebut ke sebuah file. Tahap ini dipercayakan kepada model dengan kemampuan penalaran tinggi.
  2. Implementasi. Sub-agent pekerja menulis kode sesuai rencana kerja tersebut. Jika perencanaannya matang, bagian ini cukup dikerjakan oleh model yang lebih cepat.
  3. Review dan Perbaikan. Menyerahkan diff/perubahan kode ke agent terpisah yang tidak tahu proses implementasi untuk direview, lalu memperbaiki temuannya secara iteratif hingga bersih dari catatan kritis. Mengotomatiskan langkah 3–4 pada Tahap 6 secara berulang.
  4. Laporan. Merangkum apa yang dibuat, apa saja catatan review, dan perbaikan apa yang dilakukan. Manusia tinggal membaca ringkasan ini dan menguji kriteria selesai untuk memutuskan merge.

Untuk proyek hobi atau aplikasi sederhana, otomasi sekompleks ini belum diperlukan. Cukup gunakan 2 prompt Tahap 6 pada dua sesi obrolan terpisah, Anda sudah mendapatkan sebagian besar manfaat utamanya.

Cara Membuat Slash Command Sendiri (Panduan Dasar)

Slash command hanyalah file Markdown biasa

Jika Anda meletakkan file bernama issue-create.md di dalam folder .claude/commands/ proyek Anda, Anda dapat menjalankannya dengan mengetik /issue-create. Isinya hanyalah instruksi biasa seperti "Tolong jalankan langkah-langkah berikut", di mana prompt Tahap 5 di atas dapat langsung disimpan sebagai perintah pertama Anda.

Mencoba menyimpan prompt Tahap 5 ke dalam .claude/commands/issue-create.md adalah langkah awal yang sangat bagus untuk merasakan kemudahannya.

Tuliskan aturan tetap proyek di dalam file CLAUDE.md

Jika Anda meletakkan file bernama CLAUDE.md di folder utama proyek, Claude Code akan selalu membacanya sebelum mulai bekerja. Aturan penting seperti "Dilarang menambah fitur tanpa Issue", "1 Issue = 1 PR", atau "Teknologi yang digunakan harus sesuai dokumen desain" dapat dicatat di sini agar Anda tidak perlu mengulang instruksi di setiap sesi percakapan.

Sangat disarankan untuk memindahkan keputusan-keputusan dari Tahap 1–5 (terutama bagian "Teknologi yang Digunakan" pada Dokumen Desain) ke file ini secara bertahap.

Langkah Selanjutnya

Jangan langsung memulai pada aplikasi impian Anda yang berskala besar; cobalah selesaikan satu putaran penuh pada proyek kecil terlebih dahulu. Untuk kasus sederhana seperti aplikasi temu komunitas ini, Tahap 1 sampai Tahap 5 biasanya hanya memakan waktu 2–3 jam dengan sekitar 5 buah Issue.

  • Setelah menyelesaikan 1 putaran penuh, tulis 3 baris refleksi. Di tahap mana Anda sempat bingung? Issue mana yang ternyata terlalu besar? Evaluasi ini akan membuat cara Anda membagi tugas di proyek berikutnya jauh lebih matang.
  • Pindahkan aturan yang terbukti efektif ke catatan permanen. Prinsip-prinsip seperti "Menentukan batasan yang tidak dibuat sejak awal" atau "Kriteria selesai harus bisa diuji secara visual" yang terbukti ampuh sebaiknya dicatat di panduan proyek (seperti CLAUDE.md) agar selalu dibaca oleh AI.
  • Simpan dokumen kebutuhan, spesifikasi, dan desain di dalam repositori. Jika dokumen hanya tertinggal di jendela obrolan chat, dokumen tersebut tidak akan terbaca di sesi obrolan berikutnya. Simpanlah di folder seperti docs/ dan tautkan dari Issue Induk.
